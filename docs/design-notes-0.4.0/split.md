# Package split: three packages, modular inside (owner, 2026-11-20)

The owner asked whether Super Plot could be split, since some users need only the basic charts, the 3D charts or
one particular chart, or a more modular build. The approved proposal: keep the three npm packages (`core`, `web`,
`react`), do the modularity inside them, and keep the all-in-one entry. Versions were not touched here.

| Item | Done? | How | Saving | Notes for the owner |
|---|---|---|---|---|
| Chart groups | Yes | `/charts/basic` (bar, line, area, scatter, pie, donut, histogram, box, heatmap), `/charts/business` (waterfall, bullet, funnel, waffle, timeline, gauge), `/charts/stats` (violin, beeswarm, parallel, radar, bump, calendar), `/charts/maps` (choropleth, bubble-map, column-map, flow-map), `/charts/hierarchy` (treemap, sunburst, sankey), `/charts/3d` (scatter3d, surface), `/charts/text` (wordcloud). Each exports its charts and one array (`basicCharts`, `businessCharts`, `statsCharts`, `mapCharts`, `hierarchyCharts`, `charts3d`, `textCharts`); `registerCharts(defs)` in `/base`. Sources in `packages/core/src/groups/`; `/charts` still exports every chart, `allCharts` (catalogue order unchanged) and `chartGroups` | a page with the nine basic charts: web 75.8 KB gzip against 147.8 for everything | `tests/core/split.test.ts` checks every chart is in exactly one group. The array of 3D charts is `charts3d` (an identifier cannot start with a digit). Gauge sits in business and calendar in stats, as specified |
| Transform steps as registrable steps | Yes | `transform.ts` (in `/base`) keeps the step names, keys and limits, the registry (`registerTransforms`, `registerTransform`, `transformTypes`) and the loop that checks each step's shape; `transforms.ts` (`/transforms`) holds one `TransformDef` per step (`filterStep` ... `indexStep`, `allTransforms`), `TRANSFORM_DOCS`, `filterRow`, `bucket`. The package root registers all of them | core `/base` with no chart 25.1 -> 19.9 KB gzip (with the canvas and projection moves below; the steps are 5.2 KB of a `/base` + basic page) | A step that is not registered is the error `transform_not_registered` at `transform[i].<step>`, with a hint naming `registerTransforms` and the step's export: never skipped. The JSON Schema and SPEC.md still list every step (the field DSL did not change), so an agent can write a step a `/base` page did not register and gets that error back. The step code moved verbatim (each `case` became a `run`), and conformance and SPEC regenerate with no diff. The Go and Python ports always have every step, so they do not know the new code |
| Canvas renderer on demand | Yes | Web `canvas.ts` is a chunk (`canvasChunk` in `plot.ts`, the pattern of the WebGL and navigator chunks). Mark geometry the SVG path needs too (`markCenter`, `nearestMark`, `pathCenter`) moved to the static `marks.ts`. Core's `drawScene`, `drawHover`, `buildHitIndex`, `resolveColor`, `drawPatternTile` left `/base` for a new `/canvas` entry (only the chunk imports it); `dataMarkCount` (the SVG/canvas choice) moved to `scene.ts` and stays in `/base` | 18.0 KB minified (6.6 KB gzip) out of web `/base` | What changed for a page: the first chart on a page that needs canvas (`renderer: 'canvas'` / `'webgl'`, or `auto` above 4,000 marks) is drawn when the chunk arrives, not inside the constructor. Until then the plot keeps its room and what it showed (the previous drawing with its scene, or the server's markup when hydrating), so hover, `getScene()` and `onRender` always match the screen; `ready()` resolves after the first canvas frame; `toPng()` waits for `ready()`. If the chunk cannot be fetched, `load_failed` is reported and the chart is drawn on SVG for that draw. Every later plot on the page draws at once. Measured guarantees kept: hover, keyboard, hydration, print, toolbar and the e2e suite (37 tests in Chromium) pass; jsdom tests load the chunk first (`loadCanvasChunk`) and `tests/web/canvas.test.ts` tests the waiting: nothing half-drawn, SVG kept while growing past the threshold, server markup kept, an SVG chart never fetches it, the fallback when it fails |
| Map and 3D camera code on demand | Yes | The cameras and their limits (`Camera`, `CAMERA_LIMITS`, `clampCamera`; `Camera3d`, `CAMERA3D_LIMITS`, `DEFAULT_CAMERA3D`, `clampCamera3d`, `camera3dOf`) moved to `geo/camera.ts` and `camera3d.ts`, which `/base`, the schema and `plot.ts` need. The projections (`makeView`, `project`, `projectFlat`, `unprojectFlat`, `dragCamera`, `zoomCamera`, `defaultCamera`, `slerp`, `angularDistance`, `worldOutline`, `OBLIQUE`, `arcPoints`, `makeView3d`, `project3d`, `dragCamera3d`, `zoomCamera3d`, `EYE_DISTANCE`) moved from `/base` to a new `/view` entry. `isMapType`, `is3dType` and the 3D limits moved to `charts/kinds.ts`, because re-exporting them from the chart files made `/base` reach the projections | `geo/view.ts` (4.8 KB minified) out of web `/base`; it is now a 1.8 KB gzip chunk shared by the map controls and the WebGL layer | A page that registers `/charts/maps` or `/charts/3d` carries the projections statically, as before. `/view` is for code that draws or moves a map itself |
| Sound on demand | No, measured and left static | `sonifyNotes` stays exported from web `/base` | would be 3.2 KB minified, 1.6 KB gzip | The blocker named in OPEN-DECISIONS was the export; moving it is easy, but it is not the real one: `sonify()` returns a controller whose `notes` are there at once, and it reports `sonify_empty` or `sonify_unavailable` before it returns. Both need the note plan, which is the bulk of `sound.ts` (wp9 measured the playback alone at 0.8 KB). Loading it on demand would hand back a controller with no notes yet, a change to a public contract for 1.6 KB. Settled in OPEN-DECISIONS. A `/sound` subpath was not added, since it would not change any bundle |
| Size budget | Yes | `scripts/size.mjs` cases: core `/base` with no chart, with bar (validate, render), with `/charts/basic`, with basic and `/transforms`, everything; web `/base` with no chart, with bar and line, with `/charts/basic`, everything; and the web `/base` chunks loaded on demand. `--check` fails above a budget set about 3% over today's measurement (`scripts/size-budget.mjs`, tested); `npm run gate` runs it after the build | | Budgets are in `scripts/size.mjs` next to each case: raising one is a visible change in review |
| One file per module in `dist` (not on the list: found while measuring) | Yes | `scripts/build.mjs` compiles every source file on its own (esbuild, `bundle: false`) instead of one bundle per entry with shared chunks; `npm run size` measures the built packages (`tsconfigRaw`), no longer the sources through the checkout's tsconfig `paths` | an app importing the old `dist`: core `/base` 72.9 KB gzip, web `/base` 99.1, web `/base` + bar + line 133.7 (measured the same way); now 19.9, 40.3, 63.3 | The published numbers were measured on the sources, which a user never gets. Inside a file it keeps, a bundler only drops statements it can prove free of side effects, and the chart objects (built with object spreads and calls) are not: so every chart that shared a `dist` chunk with `/base` came along. A per-module `dist` gives the user's bundler the same files as the sources, so `sideEffects` and tree shaking work, and a dynamic `import()` stays its own chunk. Web `./element` now points at `dist/element-entry.js` (the file name of its source). check-package now holds every `packages.mjs` entry to its `package.json` export, imports every core entry in plain Node, and fails if web, react or core `/base` reaches a lazily loaded or separately registered module through static imports |

**Entry points after the split.** Core: `.`, `/base`, `/charts`, the seven groups, `/transforms`, `/canvas`, `/view`,
`/tools`, `/adapters`. Web: `.`, `/base`, `/element`, `/global`. React: `.`, `/base`. The package roots register
every chart and step and re-export every entry point, so `import { renderToSvg } from '@supersolutions/super-plot-core'`
works as before (conformance and SPEC.md regenerate with no diff; the ports and their fuzzing agree).

**Moved out of core `/base`** (still in the package root; a breaking change only for `/base` imports, fine before the
first publish): `drawScene`, `drawHover`, `buildHitIndex`, `resolveColor`, `drawPatternTile` (to `/canvas`); the
projection functions listed above (to `/view`); `TRANSFORM_DOCS`, `filterRow`, `bucket` (to `/transforms`).

**Not split, and why.** Zoom and brush gestures, the stylesheet, the colour-vision check and drill-down: as in wp9.
"Everything" grew 1.4 KB gzip (123.5 -> 124.9): the steps as objects, the group arrays and the registries.

**For the owner to revisit.** The group boundaries (gauge in business, calendar in stats, heatmap in basic) are the
ones approved; moving a chart between groups later is a breaking change for `/base` users, so it is worth confirming
before the first publish. The first canvas frame now waits for a chunk (one request, once per page); a page that
needs a dense chart in its very first frame would need a way to load the canvas code statically (an entry that imports
it), which was not added since nothing asks for it yet.
